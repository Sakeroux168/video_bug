## ④ 剩余缺口（按严重度排序）

1. **中｜`parseAuthorsCsv` 表头识别在特定命名下会把表头行泄漏成一条假数据**（`src/renderer/src/components/authorsCsv.ts` 的 `pickByHeader`）。
   复现：CSV 表头是 `作者链接,备注`（单元格「作者链接」同时含名称词「作者」与链接词「链接」）。
   `pickByHeader` 先用 `findIndex` 让 url 列抢到这一列（含「链接」），然后名称列搜索把这一列排除（`i !== url`），
   由于没有第二个候选列命中名称词，`name` 判定为 `-1`，整体返回 `null`。
   调用方 `parseAuthorsCsv` 把「识别不到表头」等同于「rows[0] 就是数据行」（未表头场景的合理假设），
   于是把表头文字原样当成第一条作者记录产出（`{nickname:'作者链接', url:''}`）。
   **影响**：不会破坏后面真实数据行的解析（真实数据行仍然通过按内容猜列正确识别），
   但导入结果里会**多出一条来自表头文字的假失败行**（reason 会是「未识别到抖音主页链接」之类），
   容易让用户误以为自己表格的第一行数据有问题。已用测试锁定现状（见 ③），**未修改生产代码**，是否需要改进列识别/表头检测逻辑（例如同时检查 `rows[0]` 是否「看起来像数据」而非纯粹依赖 `pickByHeader` 是否为 null）留给项目负责人裁决。

2. **中｜作者行在任务 run 之前被删除时，「名称强绑定链接」校验被静默跳过**（`src/main/scheduler.ts` 的 `verifyImportedAuthor`）。
   `listAuthors(this.deps.db).find(a => a.sec_uid === secUid)` 找不到行就直接 `return false`（视同「不需要校验」），
   与 `verify_state !== 'pending'` 的正常放行分支走的是**同一条代码路径**，语义上把「无需校验」和「无法校验」混为一谈。
   **影响**：如果用户导入作者后、任务真正开始爬取前手动删除了这一行（或有其它竞态导致行消失），
   任务会**无提示地继续跑**，不会有任何校验相关的暂停或 `task:notice`，行为上和「这个作者本来就不需要校验」完全一样，
   用户无法区分。已用测试锁定现状（见 ③），**未修改生产代码**，留给项目负责人裁决是否需要改为「找不到作者行也报错暂停」。

3. **低｜作者表无分页，`copySelected`/`toggleAll` 在超大作者列表下的表现未验证**：当前测试用 3 行验证了「全选后复制」的完整性，
   但账本与代码都未见作者表分页机制；若作者数量增长到成百上千，是一次性渲染全部 `<tr>`，性能与全选体验未做验证（人工验收/性能测试范畴，非本轮 TDD 单测能覆盖）。

4. **低｜`authors:import` 逐行独立 `INSERT`，未包事务**（账本已记录为 deferred）：中途异常时已处理的行保留，
   符合「尽量导入」语义，非 bug，仅记录延续性风险。

5. **低｜作者去重 O(n) 归一化比对**（账本已记录为 deferred）：`insertAuthorIfAbsent` 走 `INSERT OR IGNORE`（DB 唯一约束），
   但 `task:create` 侧的作者去重仍是取全部 done 作者行逐行 JS 归一化比较，量级极大时会变慢，未做索引/缓存，非本轮新增问题。

**未发现新的生产代码 bug 会导致数据丢失或崩溃**——两条「中」缺口都是「静默跳过」类的行为缺陷，不影响已导入数据的完整性。

## ⑤ 建议

1. **优先处理缺口 1（CSV 表头泄漏）**：属于纯函数层面的小修复，风险低——只需在 `pickByHeader` 返回 `null` 时，
   额外判断 `rows[0]` 是否「看起来像真实数据」（例如任一单元格命中 `looksLikeUrl`），命中则仍按内容猜、但排除 `rows[0]`
   进入 body；不命中才当作真正无表头。因为已有测试锁定现状，若采纳修复，直接把 ③ 中新增的那条测试期望值改为
   `[{nickname:'张三',url:''},{nickname:'李四',url:''}]`（不含表头泄漏行）即可验证。

2. **评估缺口 2（作者被删后跳过校验）是否需要改为显式失败**：如果「作者行消失 = 不再需要校验」是有意为之
   （比如用户删除了就是不想再管这个作者的任务），当前行为无需改动，只需在代码注释里补一句说明消除歧义；
   如果这不是有意设计，建议把 `verifyImportedAuthor` 里「找不到作者行」与「`verify_state` 不是 pending」拆成两条分支，
   前者也走类似 `author_unverifiable` 的暂停+提示路径。

3. **下一步测试投入建议**：本轮导入作者相关的主进程/校验/解析逻辑覆盖已经很扎实（20+ 条测试覆盖 9 个 commit 的核心分支），
   继续深挖该功能的 ROI 边际递减。相对更值得投入的是：
   - `docs/交接文档.md` §7 提到的旧缺口仍未处理（TaskList 批量操作跨页/搜索过滤组合，`organizer.ts` AI 分类竞态）；
   - `parseAuthorsCsv`/`buildAuthorsCsv` 属于纯函数，适合在项目负责人裁定缺口 1 后直接补几条参数化测试收尾，成本很低；
