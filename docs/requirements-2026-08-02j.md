# 需求文档：第十一轮验收修复（5秒停滞检测 + 爬不动自动自救循环）

**日期**: 2026-08-02
**状态**: 已确认（重搜上限 3 次、筛选每任务一次），待开发
**上一轮**: 筛选续爬已能自动触发；用户实测发现：爬取到 ~150 爬不动时任务**一直显示"进行中"不暂停**（根因：到底后接口零星吐数据，停滞判定永远不触发）

## 1. 背景与根因

- 现状：停滞判定 = 连续 5 轮空数据（`buildStopDecision`），但到底后抖音接口仍零星返回 1-2 条（`解析9→剩1`）→ 空轮数被清零 → 任务既不触发自救也不停止，**永远"进行中"**。
- 用户期望：爬不动时**程序自己知道**（5 秒没动 = 爬不动）→ 自动暂停 → 到底则开筛选 → 还爬不动则**重新搜索关键词** → 循环直到爬满；没策略可用时真正暂停，不是无限转。

## 2. 核心诉求（3 条，均已确认）

### ① 5 秒停滞检测（替代 15 秒规则）

- 每轮检查 `Date.now() - lastFetchedAt > 5000`（阈值 15s → **5s**）即判停滞；**不再依赖空轮数**（空轮数仅作辅助日志）。
- 停滞 = 爬不动信号，进入自救循环或停止判定。

### ② 爬不动自动自救循环（直到爬满）

停滞时的策略顺序（任务启用筛选续爬时）：
1. **看有没有到底**（findBottomText，带可见性+视口校验）→ 到底：
   - 筛选未应用过（`!filterApplied`）→ **应用抖音筛选**（现有 applyDouyinFilter 全链路）→ 重置停滞计数继续爬。
   - 筛选已应用 → **重新搜索关键词**：`browser.load(adapter, buildSearchUrl(query, filters))` 重载搜索页（结果集重置；`seen` 去重保证只收新条目）→ `reSearchCount++` → 重置停滞计数继续爬。
2. 没到底但停滞（页面加载慢等）：连续 2 轮停滞且无到底文案 → 同样走重搜（计入上限）。
3. **循环直到 `fetched >= target`**；重搜次数上限 **3 次**（已确认），超限 → 自动暂停 + notice「已重搜 3 次仍爬不满，请调整关键词或筛选条件」。
4. 筛选每任务**只应用一次**（已确认，filterApplied 语义不变）。

### ③ 无策略可用时真正暂停（不再无限"进行中"）

- 5s 停滞 + **未启用筛选续爬**（或策略已用尽）→ 自动暂停（`paused`，error 标记如 `stalled`）+ notice「爬取停滞，已自动暂停」——替代现在的无限转。
- 恢复：用户可「继续」（重新 run，filterApplied/reSearchCount 重置——现有 resume 语义）。
