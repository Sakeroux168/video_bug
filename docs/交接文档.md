## 0-D. 最新状态（第 20 轮，2026-09-29，覆盖下文所有旧描述）

用户两件事：①「用户页可以自己选择时间，选什么时间到什么时间内的视频」（可选功能）；
②「下载时有个人一直卡着说运行中，动也不动，其他的都排着队」。版本号 0.1.0 → **0.1.1**（产物 `dist/video-scraper-0.1.1-portable.exe`）。

**一、作者主页可选日期段（默认不开 = 原来的行为）**

- 作者收藏页 → 点某行「爬主页」→ 面板里多一个勾选框「只要这段时间发的」，勾上后出现「从」「到」两个日期框。
  两个都填 = 这段时间；只填「从」= 从那天到现在；只填「到」= 那天及以前；一个都不填 / 开始晚于结束 → 「开始爬取」灰掉并提示
  「请至少选一个日期」/「开始日期不能晚于结束日期」。填对了面板会显示「只要 2026-09-01 到 2026-09-20 发的（按北京时间，含当天）」。
- 筛选表单选「作者」时，「时间」下拉多一个「自定义」，同样两个日期框（关键词/话题没有这个选项——搜索结果不按时间排）。
- 两处都会带 `allowDuplicateAuthor: true`：按日期段抓通常就是补抓以前爬过的作者，不能被「该作者主页已爬取过」去重拦掉。
- 校验和说明文字在 `src/renderer/src/components/dateRange.ts`（两处共用）。
- **日期按北京时间整天算**：`extractor.ts` 新增 `chinaDayStartSec/chinaDayEndSec/chinaToday`，固定 `+08:00`（不看电脑时区）；
  `matchTimeRange` 以前用 UTC（`T00:00:00Z`），差 8 小时，而且必须两个日期都有才生效——现在起止任一可空。
  `scheduler.pastRange`（翻过起点就算抓完）的起点也改成北京时间；本机接口 `/job` 不给 endDate 时默认「北京时间的今天」。
- **结束日期在过去时的坑**：作者主页最上面是比结束日期还新的作品，要先翻过去。以前这些批次一条不留 → 累计空轮 3 次就当「风控」暂停，
  或迟迟没有新视频 → 判停滞 → 重搜把页面拉回顶部，永远到不了日期段。现在 `handleRaw`：作者 + custom + 有 endDate，
  这一批里有比结束日期还新的 → 算「有进展」（刷新 lastFetchedAt、空轮清零），只打一次日志「正在往下翻 X 之后发的作品…」，接着滚。

**二、任务卡住 / 后面排队的永远等着**

根因有两层：
1. 队列（原 `index.ts` 的 dequeueAndRun）**只在 task:done 时放行下一个**。任务暂停（任何原因）、失败、调度出错、`run()` 早退
   （平台不存在时一个事件都不发）——后面排队的全部永远「等待中」。
2. 调度器的几处页面调用 `webContents.executeJavaScript`（查验证码 / 查到底文案 / 读作者昵称）**没有超时**。页面卡死时它永远不返回：
   `rescueStall` 卡住 → `rescuing` 一直为 true → 心跳直接 return → 主循环空转，任务一直「进行中」一动不动；
   而且「暂停」「删除」按钮 await 的是 run 退出，也跟着卡死。

改法：
- **新 `src/main/taskQueue.ts`**（从 index.ts 抽出，可单测）：当前任务**只要结束**（done / 任何 paused / scheduler_error / 看门狗判卡住 /
  run 的 promise 结束）就放行下一个。**唯一例外：弹验证码（stalled_verify）按住不放**——要等人去浏览器过验证，接着跑下一个会把验证页冲掉、
  下一个多半也被拦；等有任务重新跑起来（用户点「继续」）或用户手动新建/删除任务时再放行。暂停的任务不会被自动重新排队（不循环重试）。
- **页面调用超时**：`browser.ts` 新增 `evalInPage`（15 秒，`JS_EVAL_TIMEOUT_MS`），三处查询都走它，超时按「没查到」处理；
  `withTimeout` 现在会清掉计时器。新增 `resetPage()`：叫停滚动 + `webContents.stop()` + `reload()`，全部发出去不等。
- **看门狗**（`scheduler.startWatchdog`）：独立计时器，每 5 秒检查一次，「多少次检查都没进展」计时（不看墙上时钟，电脑睡眠不误判）。
  进展 = 本任务的接口数据来了 / 滚完一轮 / 页面加载完 / 重搜加载完。默认 **5 分钟**没进展（设置页「卡住判定(分钟)」，`settings.stuckTimeoutMin`，
  下限 2 分钟 + 滚动间隔）→ `forceStop`：**不等**卡住的 run，直接写 `status='paused', error='stuck'`、刷新页面、清掉调度器运行状态、
  发 `task:paused(reason=stuck)`（队列据此放行下一个）+ 提示「有个任务卡住了（5 分钟没动静），已自动跳过，排队的任务接着跑；可在任务列表点「继续」重试」。
- **旧 run 醒来不许乱动**：`runGen` 代号——每次 run +1，强制停止再 +1。旧 run 醒来后所有检查点（`stopped()`、写库、发事件、finally 收尾、
  rescueStall 里每次 await 之后）发现代号不对就直接退出，不会改掉「卡住」标记，也不会清掉下一个任务的状态。
- **暂停/删除不再卡死**：`pause()` 最多等 10 秒（`PAUSE_WAIT_MS`，deps.pauseWaitMs 可调），等不到就 forceStop('user')。
  ipc `task:pause` 只在「正在跑的就是它」时叫停调度器（以前不管暂停哪个都会停掉正在跑的），暂停排队中的任务 = 从队列摘掉。
  ipc `task:resume`（「继续」/「开始」）：别的任务正在跑时改为放回队列排队（以前 run 发现在忙直接 return，按钮点了没反应）；
  直接开跑时先从队列摘掉，避免跑完又被队列再跑一遍。
- 界面：任务列表里 `paused + error='stuck'` 的状态列显示「卡住了，已跳过」，下面一行黄条「卡住了，已跳过（可点「继续」重试）——
  这个任务好几分钟没有任何进展，已自动停下，排队的任务接着跑了」。
- **下载卡住**（`downloader.ts`）：视频下载加「无数据超时」60 秒（`DOWNLOAD_IDLE_TIMEOUT_MS`，每收到一块数据重新计时，慢但在传的不算）——
  超时抛普通错误 → 归为 network → 走原有的「自动重试 2 次」。用单独的 AbortController，和用户取消/暂停的 aborter 分开，catch 分流不变。
  封面最多下 60 秒（超时只是不要封面）；ffprobe 校验最多 30 秒（超时被杀按「跳过校验」放行，和找不到 ffprobe 一样）。

**测试**：962 条全绿（上一轮 913）。新增 `tests/task-queue.test.ts`（队列放行规则）、`tests/browser-eval-timeout.test.ts`（页面调用超时 / resetPage）；
`scheduler.test.ts` 加 R20 三组（比结束日期新的批次算进展、北京时间边界、看门狗强制停 + 旧 run 不乱动、pause 不卡死、早退发事件）；
`extractor.test.ts`（+08:00 边界、只填一头）；`downloader.test.ts`（无数据超时重试、慢速不误伤）；组件测试 `author-crawl-home` / `filter-form` / `tasklist-smoke`。
FakeBrowser 加了 `resetPage` spy；设置相关测试夹具加了 `stuckTimeoutMin`。

**行为变化提醒**：用户点「暂停」正在跑的任务后，排队的下一个会自动开跑（以前会一直等着）。没真机跑过（按规定只做了单测/类型检查/构建），
看门狗的 5 分钟、页面调用的 15 秒都是估计值，真机若误伤正常任务就调设置页「卡住判定(分钟)」。

  查找顺序 = `process.resourcesPath`（打包后包内那份，优先）→ 各盘 `/123/ffmpeg<版本>/bin/`
  → 原生扫 `process.env.PATH`。**不再 shell out `where.exe`**——中文 locale 下它按 GBK 输出，

  从没走到兜底，所以这坑藏了 13 轮）。
- **停滞阈值有了动态下限**：`minStall = (scrollIntervalMs+1500)/1000 + 5.5 + 5`（默认 15.5s），
  实取 `max(用户值, minStall)`，抬高时打日志说明、不静默覆盖。
  **背景**：阈值小于「等待阶段 + 滚动到首批数据回来」时，心跳会把正常滚动判成停滞并
  `abortScroll` 掐断 → 没滚到底 → 不触发懒加载 → 无新数据 → 重搜重载 → 死循环卡在第一页，
  且界面无任何可辨识信号。真机验收时表现为「程序不会自己往下滑」。
- **`scrollIntervalMs` 改为每次 run 现读**（原为构造时读死，设置页改了不重启不生效）。
- **副作用（已知）**：动态下限固定分量 10.5s > 默认重搜冷却 10s，「重搜冷却」设置项实际已失效
  （保护改由更严的停滞阈值执行，间隔 ≥15.5s）。设置页那个输入框目前是摆设。

## 1. 这是什么

**抖音视频批量爬取桌面程序**（Electron + React + TS）。内嵌抖音浏览器（独立窗口）扫码登录 → 按关键词/作者/话题抓取 → 无水印下载 → 按 `品类\作者\一分钟内|外\` 归档 → 可选 AI（本地 sherpa 中文转写 + 多模态视觉）判定作者品类。历经 10 轮验收修复，当前 280 个测试全绿、typecheck/build 通过。

## 4. 核心机制速览

- **抓取**：浏览器窗口滚动（页面级中止信号：暂停 1 秒内停）→ 注入 fetch/XHR 挂钩把接口 JSON 发给主进程 → `scheduler.handleRaw` 按任务类型过滤接口 → 解析（`aweme_info` 包装解包）→ 去重(seen) → **硬截断到目标数**（不多插一条）→ 入库。
- **自救循环**（见 §0）：停滞（秒级心跳）→ 验证码优先 → 到底检测（DOM 文字+可见性+视口校验）→ 重搜（冷却+≤3 次上限）。长操作强制超时（load 30s/滚动 60s）。
- **下载**：全局队列并发 3；`playwm→play` 无水印变体回退；ffprobe 视频轨校验（黑屏防护）；暂停/取消/单条暂停用 AbortController 掐断（abortReasons 快照区分全局暂停/单条暂停/取消）；重启只重排 pending，paused/collected 不动；删除视频 = 文件+记录+作者计数联动。
- **归档**：下载完成自动触发（**不依赖 AI 勾选**）→ 按作者分类（AI 听+看 → 作者已有品类 → 未分类）→ 移入 `下载目录\品类\作者\一分钟内(≤60s)|一分钟外\`；幂等（只移平铺层文件）。
- **诊断**：顶部「查看拦截日志」面板显示所有接口与 `[筛选]`/停滞自救日志（停滞检测/验证码命中/重搜记录）。
